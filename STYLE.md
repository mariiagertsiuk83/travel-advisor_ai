# STYLE.md

## Code

- Follow the existing project style first.
- Prefer simple, readable code in the languages and frameworks already approved for the repository.
- Keep components small and focused.
- Use explicit types for public props and shared data shapes.
- Prefer direct solutions and avoid premature abstractions.

## Responses

- Respond in Ukrainian.
- Lead with the result or next useful step.
- Keep responses short, practical, and easy to scan.
- Use exact file names, commands, checks, branches, and commit hashes when they matter.
- Avoid unnecessary theory and excessive formatting.

## Markdown And Documentation

- Use short headings and lists only when they improve readability.
- Avoid duplicated content, placeholders, and mixed document purposes.
- Use the language of the existing document unless the user asks otherwise.
- Keep claims bounded by available evidence; do not promise unconfirmed capabilities, guarantees, or outcomes.

## Comments

- Comment only when explaining why something exists or clarifying a non-obvious decision.
- Do not comment obvious code.
- Do not leave bare TODO comments; include context and the condition for returning.

## Naming

- Use English for code, file names, technical identifiers, and commit messages.
- Use `PascalCase` for components.
- Use `camelCase` for functions and variables.
- Use `SCREAMING_SNAKE_CASE` only for true global constants.
- Prefer names that express domain meaning.

## Structure

- Follow the existing directory structure.
- If no scaffold exists, use the smallest structure supported by approved architecture sources.
- Keep screens, reusable components, data/types, and configuration concerns separate.
- Avoid deep nesting and speculative abstractions.

## Commit Messages

- Use short English imperative phrasing.
- Keep each commit focused on one change.
- Do not add a period.

Examples:

- `Add component contract`
- `Update operating instructions`
- `Fix route validation`
